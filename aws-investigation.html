Step 2 of 5 · V.I.T.A.L.

Investigate

Determine the exact access path. Eliminate known-good activity; isolate the compromised credential or role.
  • IAM user review: Customer has 3 IAM users. All three reviewed for access key usage, console sign-in history, and MFA status. No anomalous activity attributed to any IAM user.
  • IAM role scope: 47 roles in account. Filtered to roles with trust policies permitting cross-account assumption. Reduced to 11 candidate roles.
  • Identified role: arn:aws:iam::REDACTED:role/dev-deploy-role — trust policy permits assumption from any AWS principal possessing the ExternalId.
  • Attached policy: AdministratorAccess (AWS managed). No permission boundary configured.
  • ExternalId entropy: Value is deploy-2023 — a static, low-entropy string. High probability of exposure via public repository (Git commit history, CI/CD config leak).
dev-deploy-role — Trust Policy (Extracted) ⚠ Critical Misconfiguration 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"AWS": "*"},   // ← any AWS account in the world
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": {
        "sts:ExternalId": "deploy-2023"  // ← static, low-entropy; likely leaked
      }
    }
  }]
}
Access Path Identified
Any AWS principal possessing the ExternalId deploy-2023 can assume dev-deploy-role and inherit full AdministratorAccess with no permission boundary. The wildcard principal eliminates any account-level restriction. ExternalId was intended as a shared secret but was stored in a manner consistent with repository exposure.

Step 4 of 5 · V.I.T.A.L.

Assess

Classify severity, enumerate the blast radius, and quantify confirmed exposure before driving remediation.
Overall Severity: Critical
  • Financial exposure: $47,203 confirmed in unauthorized compute (EC2) and storage (S3 egress) charges. Additional charges may accrue pending final billing reconciliation.
  • Data at risk: S3 access confirmed across 3 buckets. Data classification is the customer's responsibility — investigator cannot confirm PII vs. operational data without customer disclosure. Customer advised to conduct their own data sensitivity review.
  • Persistence mechanism: IAM user backup-svc created by attacker using assumed role's AdminAccess. This user holds separate, independent long-term credentials. Policy remediation on dev-deploy-role alone would not revoke attacker access.
  • Blast radius: Confirmed single AWS account. No evidence of lateral movement to other accounts in the Organization. Cross-account trust from attacker account only.
  • Root cause decomposition: Wildcard trust principal + static low-entropy ExternalId + AdministratorAccess with no permission boundary. Three compounding failures with no compensating control at any layer.

Step 5 of 5 · V.I.T.A.L.

Lead Remediation

Define, sequence, and drive the resolution path. Separate immediate containment from structural controls to avoid analysis paralysis under active incident conditions.
Phase 1 — Immediate Containment 0 – 2 hours
  • 01 Revoke all active sessions for dev-deploy-role. Replace trust policy via aws iam update-assume-role-policy with an explicit deny-all statement. Active sessions using existing assumed-role credentials remain valid until expiry; monitor for activity in the 0–60 minute window post-revocation.
  • 02 Delete attacker-created IAM user backup-svc and all associated access keys. This user was created with AdminAccess and holds persistent credentials independent of the compromised role.
  • 03 Rotate all existing IAM user access keys. Attacker possessed AdministratorAccess during the 6-day window — treat all existing long-term credentials as potentially exposed.
  • 04 Identify and terminate all unauthorized EC2 instances: 14 instances (c5.4xlarge) in us-east-1, 8 instances (c5.4xlarge) in eu-west-1. Tag-based filtering not reliable — cross-reference with RunInstances events from the compromised role session.
  • 05 Enable CloudTrail in eu-west-1 immediately. Attacker's region selection exploited the monitoring gap. Confirm trail is logging to a secure, separate-account S3 bucket.
Phase 2 — Short-Term Hardening 2 – 24 hours
  • 06 Audit S3 access logs for the 3 affected buckets. Determine whether data was copied externally. Scope: check for GetObject events with the attacker session ARN, correlate with the 847 GB egress volume. Customer to assess whether data warrants breach notification review.
  • 07 Review all 47 IAM roles for similar trust policy patterns — wildcard principals ("AWS": "*" or "*") or static ExternalId values. IAM Access Analyzer can accelerate this when enabled.
  • 08 Remove AdministratorAccess from dev-deploy-role. Apply a least-privilege replacement policy scoped to the role's actual deployment function. No developer role should carry AdminAccess in a production environment.
  • 09 Attach permission boundaries to all developer-facing IAM roles. A boundary limits the maximum effective permissions regardless of attached policies — containing the blast radius of future misconfigurations.
Phase 3 — Structural Controls 24 – 72 hours
  • 10 Implement an SCP blocking sts:AssumeRole from principals outside the Organization. Apply at the Organization root or relevant OU. This closes the wildcard trust policy class of vulnerability at the infrastructure layer, independent of role-level configuration.
  • 11 Rotate ExternalId to a high-entropy value (≥32 random characters). Store in AWS Secrets Manager. Rotate programmatically — no human-readable, guessable, or historically repeated values.
  • 12 Enable IAM Access Analyzer across all accounts in the Organization. Access Analyzer flags externally-accessible IAM roles and S3 buckets as findings — this misconfiguration would have been surfaced at creation time with Access Analyzer active.
  • 13 Establish billing alert thresholds at $500 incremental (hourly granularity where available via CloudWatch Billing). Customer's existing $50,000 threshold provided no meaningful early detection — the attacker spent $7,000+/day for 6 days before the alert fired.

Investigator Note — Janaya Hoskins
This case is representative of a recurring pattern in AWS customer escalations: a developer shortcut — wildcard trust principal combined with a static, low-entropy ExternalId — left in place past its original use case, then combined with an overly permissive role. The result is an open invitation for cross-account abuse available to any actor who discovers the ExternalId, whether through repository exposure, configuration leaks, or enumeration.

The attacker's deliberate selection of eu-west-1 — not an active customer region — is a calculated evasion of alerting scoped to expected regions. This is a known attacker behavior pattern: cloud fraud campaigns regularly probe for monitoring blind spots before beginning resource provisioning.

Billing alert thresholds set at $50,000 per month provide no meaningful early detection against fraud campaigns operating at $7,000 or more per day. By the time the alert fired, six days of charges had accrued and a persistence mechanism had been established. Detection should come from security tooling — Access Analyzer, GuardDuty, CloudTrail anomaly detection — not from billing thresholds.
— Janaya Hoskins · Technical Customer Support Specialist · Amazon Web Services
