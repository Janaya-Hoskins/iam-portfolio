Why Native Tooling Is Not Enough

SailPoint IdentityIQ surfaces what it knows. If a connector is drifted, a correlation rule is misconfigured, or an authoritative source has diverged from the SailPoint view of reality, the platform will report its internal state — not the actual access state. The same gap exists in any platform: the tool reports what it ingested, not what is true in the underlying system. My SQL and Python work exists to close that gap — to compare what the platform believes against what authoritative sources actually contain.

SailPoint C&A Automation (CVS Health)
  • Cross-system identity matching: Python scripts that join SailPoint identity records against authoritative HR and application data — flagging accounts where the SailPoint identity object does not match the authoritative employee or contractor record, catching correlation failures before they enter a certification campaign.
  • Population completeness validation: SQL queries that compare SailPoint's certified population against raw application user extracts — identifying accounts in the application that SailPoint has not aggregated, which would produce an incomplete certification and a population gap finding.
  • Entitlement discrepancy detection: Row-level comparison between SailPoint entitlement data and authoritative application role assignments — flagging entitlements that exist in the application but are not reflected in SailPoint, and vice versa. Either condition is a C&A failure.
  • Connector drift identification: Logic that detects when SailPoint aggregation timestamps diverge from expected connector schedules — surfacing stale data conditions before a campaign is configured on outdated population data.
CloudTrail Investigation & Fraud Detection (AWS · BGE)
  • CloudTrail SQL analysis: SQL queries against AWS CloudTrail logs to reconstruct access chains — extracting the specific API calls, AssumeRole events, credential usage, and data-access events that constitute an escalation or suspected fraud investigation. The query identifies who, what, when, from where, and through which policy — building the evidentiary chain before the analyst interprets it.
  • Access-path reconstruction: For cross-account access anomalies, queries that trace the full assume-role chain — from the originating principal through trust relationships, session policies, and permission boundaries — to identify the exact policy combination that permitted unauthorized access.
  • Risk-scoring rules (BGE): 25+ SQL-based detection rules incorporating identity-mismatch indicators, behavioral signals, and consumption anomalies — the same pattern-matching logic applied to utility fraud investigation that I now apply to IAM discrepancy detection.
  • Reporting automation: Power Query and VBA automation at Exelon eliminating 35+ hours of monthly manual validation — pulling data, running comparisons, and surfacing exceptions automatically rather than requiring analyst effort for data assembly.
The throughline: Whether the dataset is SailPoint identity records, CloudTrail API logs, or utility account data, the analytical pattern is the same — extract, compare against an authoritative source, classify discrepancies by type and risk, and produce a documented finding with a recommended remediation path. SQL and Python are the execution layer. IAM domain knowledge is what determines which discrepancies matter.

C&A Operating Model & Workflow Redesign — Self-Initiated Governance Architecture

Process Design Jira Agile / Scrum IGA Operations SOX Governance
The Problem

C&A validation — the pre-campaign quality gate that determines PAR readiness across 20+ enterprise applications — was tracked through three weekly review meetings, a shared spreadsheet, and ad-hoc email follow-ups. The failure was structural: the tracking approach could not enforce status sequencing, trigger escalations, surface at-risk accounts before a review cycle closed, or produce an audit-ready trail of who validated what and when. Application owners engaged reactively. Leadership had no visibility until after a deadline was missed. For SOX-designated applications, that gap was a control risk.

Important context: This was not an assigned project. I identified the control gap while executing standard C&A operations, built the full proposal and supporting materials, and brought it to leadership. In addition to this self-initiated work, I periodically backfilled operational responsibilities normally held at the 409/410 level during coverage gaps — including cross-functional coordination, escalation management, and lifecycle disposition decisions.
What I Identified

Four compounding failure modes: (1) Reactive app owner engagement — owners were contacted when their application came up in rotation, not proactively pre-campaign. (2) No SLA enforcement mechanism — there was no automated day-5 reminder or day-7 escalation path. (3) Inconsistent evidence standards — different analysts collected different documentation for the same application type, creating audit exposure. (4) No lifecycle audit trail — leadership could not answer "when was this application validated, by whom, and what evidence was collected" without digging through email.

Target State I Designed

A Jira-based operating model with 12 enforced lifecycle statuses (Pending IAM Review → IAM Onboarding in Progress → C&A Pending → C&A In Progress → C&A Validation Complete → PAR Ready → No PAR Required / Rework Required / Escalated to Leadership / Risk Accepted / On Hold / Closed), 16 tracked fields per application, automated Day-5 SLA reminders and Day-7 leadership escalation triggers, bi-weekly sprint cadence, and a proactive app owner notification sequence beginning 2 weeks pre-campaign. Status transitions are sequenced — an application cannot advance to C&A Validation Complete without clearing all prior gates.

What I Built
  • Interactive C&A Workflow: A branched decision flow — IAM intake → onboarding disposition → leadership assignment → application owner kickoff → final C&A validation → PAR readiness gate — with branch logic for exception paths (no PAR required, rework required, escalation). Each node has a detail panel describing the responsible party, action required, and SLA.
  • Jira Operating Model Prototype: Functional visual prototype with List, Board, Dashboard, Reporting, and Tracker views. Demonstrates the 12-status lifecycle, assignee accountability, SLA day-counter, and leadership escalation view — built to communicate the target state concretely, not abstractly.
  • Process Improvement Proposal: Formal written proposal documenting the current-state failure, target-state design, implementation path, and benefit case — submitted to leadership and accepted.
Implementation Constraint

Jira was not immediately available for procurement and rollout. Rather than treating that as a blocker, I designed a fully operational interim model that could function within existing tooling — Excel tracker, email, and calendar — while preserving the same schema, escalation logic, and field structure as the target-state Jira design.

What I Did Next — Interim Operating Model

The interim model uses an Excel tracker structured with the same 16 fields as the Jira design, a standardized email cadence replacing automated notifications (Day-5 POC reminder, Day-7 leadership escalation), and a calendar-driven sprint schedule. The tracker preserves the same status vocabulary so the transition to Jira requires no retraining — it is a tool swap, not a process change.

Investigation Methodology · Applied Across Case Studies 3–6 · Developed Over 3+ Years
V.I.T.A.L. IAM Investigation Framework
Structured five-step investigation methodology applied across identity governance work — C&A discrepancy investigation, PAR exception classification, access anomaly triage, and privileged account incident response. Platform-agnostic: applies equally to IGA connector drift, PAM session anomalies, and access certification exceptions.
Five-Step Methodology — Key Questions at Each Stage
V
Validate — Confirm the anomaly is real, not an artifact of data lag or connector timing. Is the discrepancy reproducible from independent data sources? Is this within expected access patterns for the account type?
I
Investigate — Determine what path access took. Which policies were evaluated? Which entitlements were active at time of the event? Does IGA Platform's view of the entitlement match the authoritative application record?
T
Trace — Build the complete access chain: identity → provisioning path → entitlement source → effective access granted. Identify every hop. In audit logs: who, what action, when, from where, through which access path and policy evaluation.
A
Assess — Classify the severity and blast radius. What data classification was exposed or at risk? Is this a single-account issue or a systemic pattern? What is the root cause type — provisioning failure, connector drift, policy misconfiguration, identity correlation error, or active threat?
L
Lead Remediation — Define and drive the resolution path. Document root cause, remediation action, control recommendation, and recurrence-prevention measure. Verify closure at the system level — not just the ticket level. Produce audit-ready documentation before closing.

Fraud Risk Detection Framework — Sanitized SQL Rule Sample

Sample Detection Rule — Identity Mismatch + Anomalous Consumption (Sanitized · Field Names Generalized)
-- Rule: Identity Mismatch + Elevated Consumption Indicator -- Surfaces accounts where identity verification failed AND consumption -- significantly exceeds the account's historical baseline. -- False positive rate: reduced 35% through iterative threshold tuning. SELECT a.account_id, a.account_status, a.service_address, iv.id_verification_result, iv.verification_date, c.consumption_30d, c.consumption_baseline_avg, ROUND((c.consumption_30d / NULLIF(c.consumption_baseline_avg, 0)) - 1, 2) AS consumption_variance_pct, p.days_since_last_payment, p.payment_method_change_flag FROM accounts a JOIN identity_verification iv ON a.account_id = iv.account_id JOIN consumption_data c ON a.account_id = c.account_id JOIN payment_history p ON a.account_id = p.account_id WHERE iv.id_verification_result IN ('FAILED', 'INCONCLUSIVE') AND c.consumption_30d > (c.consumption_baseline_avg * 1.75) AND a.account_status = 'ACTIVE' AND p.days_since_last_payment < 90 -- exclude long-delinquent (separate rule) ORDER BY consumption_variance_pct DESC; -- Output feeds investigation queue ranked by composite risk score. -- Root-cause classification applied at closure: diversion / misrepresentation / -- account takeover / contractor fraud / billing error.
